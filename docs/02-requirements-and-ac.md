# 02｜什麼是需求？什麼是 Acceptance Criteria？

## 需求不是「我要一個功能」

差的需求：

> 幫我把搜尋做好一點。

這句話最大的問題不是 Agent 不夠聰明，而是「做好」沒有共同定義。

比較完整的需求至少回答：

### 1. 誰遇到問題？

例如：

> 使用者有很多 LUT，不容易快速找到接近自己喜歡風格的 LUT。

### 2. 問題是什麼？

> 現在需要逐個點開比較，認知負荷很高。

### 3. 我們希望得到什麼結果？

> 使用者可以從一個喜歡的 LUT 出發，快速看到相似選項。

### 4. 有哪些限制？

> 第一版只處理現有 LUT，不做使用者上傳。

### 5. 哪些不在這次範圍？

> 不處理 LUT 編輯器、不處理帳號系統。

這些合起來才比較接近一個可以交付的 Requirement。

# Requirement、User Story、AC 不一樣

## Requirement

描述「我們需要解決什麼問題 / 達成什麼結果」。

## User Story

是一種用使用者視角表達需求的方法，例如：

> 身為有很多 LUT 的使用者，我希望從目前喜歡的 LUT 找到相似 LUT，讓我不用逐個比較。

User Story 很有用，但不是每件工作都一定要硬寫成 As a / I want / So that。

## Acceptance Criteria（AC）

AC 回答的是：

> **做到什麼程度，我們才同意這件工作完成？**

AC 應該盡量：

- 明確
- 可觀察
- 可驗證
- 有 Pass / Fail
- 描述結果，不綁死技術實作

---

# 好 AC 與壞 AC

## 壞 AC

- UI 要好看
- Search 要快
- 手機版要正常
- Agent 要考慮 edge case

問題：每個人對「好看 / 快 / 正常 / 考慮」的定義都不同。

## 比較好的 AC

- 在 390px 寬度下，主要 CTA 不會超出畫面。
- 使用者輸入沒有結果的關鍵字時，會看到「找不到結果」狀態，而不是空白頁。
- 從任一 LUT 點擊「找相似」後，畫面會顯示至少 5 個相似候選；若資料不足則明確顯示不足原因。
- 使用者重新整理頁面後，目前選擇的 collection 仍會保留。

這些條件即使不會寫程式，也有辦法驗。

---

# AC 與 Definition of Done 不要混在一起

## AC：這一件功能特別要做到什麼

例如「收藏功能」：

- 登入使用者可以收藏。
- 再按一次可以取消收藏。
- 重新整理後收藏狀態仍存在。

## Definition of Done：每一件工作共同要符合的品質底線

例如整個團隊都要求：

- 自動測試通過。
- 沒有未處理的 blocker。
- PR 有對應 Issue。
- 有 Preview 可供驗收。
- 影響 UI 時附 Before / After。
- 已知限制有被寫出來。

一句話：

> **AC 是這題的答案；DoD 是所有題目的交卷規則。**

# Agent 101 建議的需求模板

## Goal

為什麼做？想改善什麼？

## User / Context

誰在什麼情況下遇到問題？

## Scope

這次要處理哪些東西？

## Non-goals

這次明確不做哪些東西？

## Acceptance Criteria

用可以 Pass / Fail 的方式列出。

## Examples

至少放一個正常案例，以及必要的邊界案例。

## Evidence Required

做完要拿什麼證明？

- Preview URL？
- Screenshot？
- Video？
- Test result？
- Before / After？

---

# 一個重要判斷

如果你寫完需求後，仍然只能說：

> 「到時候我看一下感覺對不對。」

通常代表需求還沒被定義得足夠清楚。

不是所有產品判斷都能完全量化，但至少應該把「可以事先說清楚的部分」先變成 AC。
