# 03｜BDD：用具體例子把「我以為」變成可驗收行為

## 為什麼 Agent 101 適合教 BDD？

BDD（Behaviour-Driven Development）的價值，不是先學測試工具。

它更重要的用途是：

> **讓 business、PM、設計、工程與 Agent 對「系統應該怎麼表現」建立共同理解。**

對沒有技術背景的人，這比學 code 更直接。

---

# 先不要學 Cucumber，先學「例子」

抽象需求：

> 未登入使用者不能收藏。

這其實還有很多問題：

- 按收藏後什麼都不發生？
- 顯示登入畫面？
- 登入後要不要自動完成收藏？
- 原本頁面會不會消失？

所以把規則變成具體例子。

## Given / When / Then

### Scenario：未登入使用者收藏

**Given** 我目前沒有登入  
**When** 我在文章頁按下「收藏」  
**Then** 系統要求我登入  
**And** 不會顯示「收藏成功」

這時人與 Agent 比較不容易各自腦補。

---

# Given / When / Then 到底代表什麼？

## Given

目前已知的狀態 / 前提。

> Given 我是已登入會員。

## When

發生的行為 / 事件。

> When 我按下「收藏」。

## Then

使用者可以觀察到的結果。

> Then 收藏按鈕變成已收藏狀態。

最重要的是 Then：

> **盡量驗「外面看得到的結果」，而不是內部怎麼實作。**

非技術人員不需要知道資料存在 PostgreSQL 還是 Redis，才有能力判斷「重新整理後收藏還在不在」。

---

# Example Mapping：比直接寫一大篇規格更適合入門

可以把一張 Story 拆成四種東西：

### Story

我們想完成什麼？

### Rules

有哪些商業規則？

### Examples

每條規則有哪些具體例子？

### Questions

哪些地方目前還不知道？

例如：

**Story**  
使用者可以收藏文章

**Rule 1**  
登入使用者可以收藏

**Example**  
第一次按收藏 → 收藏成功

**Example**  
再次按收藏 → 取消收藏

**Rule 2**  
未登入不可直接收藏

**Example**  
未登入按收藏 → 要求登入

**Question**  
登入完成後，要不要自動幫使用者完成剛剛的收藏？

最後這個 Question 很重要。

Agent 最危險的行為之一，就是把「沒有決定的事情」自己補成決定。

---

# BDD 在這門課的位置

建議：

需求  
↓  
Rules  
↓  
Examples  
↓  
AC  
↓  
Ticket  
↓  
Agent 執行  
↓  
用同一組 Examples 驗收

也就是：

> **規劃時寫的例子，就是完成後拿來驗收的例子。**

這會讓「需求」與「測試」之間少掉大量翻譯。

---

# 不需要所有 AC 都寫成 Given / When / Then

簡單條件直接 checklist 就好：

- 手機寬度 390px 不出現水平捲軸。
- 頁面 title 為「Pricing」。

有狀態與行為互動時，再用 Scenario：

Given 使用者沒有登入  
When 使用者進入付款頁  
Then 系統要求先登入

重點不是格式，而是讓行為具體、可重現、可判斷。
