# 06｜BMAD 放在哪裡？

BMAD 很適合在 Agent 101 裡出現，但不建議一開始把它當必學操作框架。

比較好的定位是：

> **BMAD 是「Agent 團隊如何把需求、規劃、角色、文件與交付串成一套流程」的案例。**

---

# Agent 101 先教原理

先讓學員懂：

Goal  
↓  
Requirement  
↓  
AC / Examples  
↓  
Ticket  
↓  
Agent  
↓  
PR  
↓  
Review  
↓  
Deploy

再告訴他：

> 當專案變大，這些事情可以被制度化。BMAD 就是一種做法。

---

# BMAD 值得拿來介紹的幾個觀念

## 1. 不同問題需要不同角色視角

產品、UX、架構、開發、測試，本來就在回答不同問題。

Agent 也不應該永遠只用「一個萬能角色」處理所有事情。

## 2. 決策要留下 Durable Context

重要決策不要只留在某次聊天。

例如：

- Product Brief
- PRD / Requirements
- Architecture
- UX decision
- Story / Task
- Test plan

後面的 Agent 才不需要重新猜一次。

## 3. Process 要跟工作大小匹配

修一個 typo，不需要先生成 20 頁 PRD。

新做一個付款系統，也不適合只丟一句 Prompt 直接 coding。

所以真正重要的是：

> **Right-sized process。**

## 4. Agent 是一支團隊，不代表不要治理

角色變多，不會自動讓成果正確。

仍然需要：

- source of truth
- scope
- handoff
- acceptance
- review
- audit trail

---

# 不建議 Agent 101 一開始教的 BMAD 內容

- 安裝
- 每個 command
- 每個 persona
- 完整 artifact lifecycle
- 所有流程分支

原因很簡單：

如果學員還不知道「為什麼需要 Requirement、AC、Review」，看到 BMAD 只會像是在背一堆 Agent 名稱。

---

# 建議課程安排

### Foundation

「怎麼管理一個 Agent 做完一件事」

### Intermediate

「怎麼讓多個 Agent 分工，而不是互相踩」

### Case Study：BMAD

「成熟框架怎麼處理規劃、角色、handoff 與 context」

這樣 BMAD 是用來驗證前面學到的體系，而不是取代體系本身。
