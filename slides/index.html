01 定義工作

Agent 變強後，第一個問題反而是：
你到底要它完成什麼？

模糊委派

「幫我把搜尋做好一點。」

  • 「好」是速度、準確率，還是 UI？
  • 哪一群使用者？
  • 什麼不能改？
  • 怎樣算完成？
可委派工作
GoalContextScopeNon-goalsACExamples
Requirement / AC

需求回答「為什麼與什麼」；AC 回答「做到哪裡算完成」

Requirement
我們要解決什麼問題？
誰情境問題結果限制
Acceptance Criteria
看到什麼，我才會說「可以」？
390px 手機寬度不出現水平捲軸
搜尋無結果時顯示 Empty State
重新整理後收藏狀態仍保留

AC 要可觀察、可驗證、能 Pass / Fail；不要寫「好看、正常、考慮 edge case」。

BDD / Example Mapping

把「我以為你懂」變成具體例子

Story使用者可以收藏文章
Rule未登入不能直接收藏
ExampleGiven 未登入
When 按收藏
Then 要求登入
Question登入後要不要自動完成剛才的收藏？

BDD 不等於 Given / When / Then 語法；核心是跨角色用具體例子建立 shared understanding。未知就是 Question，不要讓 Agent 自己把未知補成決策。

Subagent

Subagent 是獨立 context 的專責 worker：適合隔離研究、實作、Review、QA

1Planner拆需求、列風險、問問題。
2Builder只做明確 ticket，不擴大 scope。
3Reviewer對照 AC，找缺漏與 scope creep。
4QA跑 scenario、edge case、regression。
Skill vs Subagent

Skill 是能力模組；Subagent 是職務角色

Skill
這類事情通常怎麼做？
投影片 skill
PR evidence skill
Survey skill
Subagent
哪個獨立 worker / context 來做？
可有自己的 prompt / tools / context
可做 Planner / Researcher / Builder
也可做 Reviewer / QA

Skill 解決「方法重用」；Subagent 解決「隔離工作與 context」。角色只是 Subagent 的常見用法之一。

03 驗收交付

非技術的人，不需要證明「code 寫得漂亮」

你要證明的是：產品行為符合事先約定的需求。

2MechanicalBuild / Test / Security checks 過了嗎？

End-to-End

最後，整套 Agent 101 只是在回答三個問題

01你要什麼？

Goal · Requirement · AC · Examples · Spec

02現在做到哪？

Ticket · Kanban · Git · Context · Skills

03你怎麼知道真的好了？

PR · Checks · Preview · Evidence · Human Acceptance

不是追求「最會寫 code 的 Agent」，而是建立「可以放心委派工作的系統」。
