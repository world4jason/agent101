Agent 101 · Human + Agent 協作入門

管 AI 專案，
本質是管工作

不先學提示詞技巧，也不先背工具。先把工作變成 可委派、可追蹤、可驗收、可交付。

01想先發散，再決定
02拆分出工作層級
03票寫清楚工作與完成條件
04做開始執行、看狀態
05審看證據、判斷是否通過
06合接受後合併 / 交付
這堂課只建立兩個核心觀念：Agent 怎麼持續工作；Human + Agent 怎麼把工作交付出去。
Agent 是什麼？

Agent = 有目標、能行動、會看結果、再繼續

目標（Goal）我要達成什麼？
→
行動（Act）做下一步
→
觀察（Observe）看結果
→
繼續（Continue）繼續、調整，或停下來問人
↺
LUT Gallery LUT 可先理解成「調色預設」。「先檢查這個專案，找出使用者為什麼很難快速挑到喜歡的 LUT。先不要改。」

Agent 不是「更會聊天的模型」。它是能為了目標 行動 → 觀察 → 繼續 的 AI 工作者。

怎麼開始？

不用先找「Create Agent」；
直接從工作介面開始

CODING AGENTCodex

開啟專案 → 說清楚要它先做什麼

CODING AGENTClaude Code

進入專案 → 直接交付一個明確工作

MULTI-STEP WORKChatGPT Work

把需要多步驟完成的工作交出去

同一段 LUT 任務 在專案工作介面輸入：「先檢查，不要直接改。」 需要指定程式碼位置時，再說「這個專案 / 程式碼資料夾」。

Agent 是一種工作能力，不一定是一個獨立按鈕。

為什麼它可以繼續做？

LLM（Large Language Model，大型語言模型）做這一步推理；
Agent/App 維持工作循環

目前輸入Current Input · 這一步需要的資訊
→
LLM判斷下一步
→
下一步輸出 / 工具請求
→
執行動作Action
→
觀察結果Observation
↺
同一個目標 Agent 讀專案 / 現有介面 → 發現「目前只能逐顆找 LUT」→ 把這個觀察結果帶進下一步

模型只對這一步拿到的工作脈絡（context）做推理。Agent/App 會把相關指令、檔案、查回來的資料、工具結果帶進下一輪；不代表每一輪都逐字重送全部歷史。

Agent 與執行環境

Agent 決定下一步；
執行環境（Environment）決定動作在哪裡發生

本機（Local）
你的電腦 / 專案 / 終端機（shell）
直接使用本機專案
執行本機工具與測試
受本機憑證與權限限制
雲端（Cloud）
平台提供的隔離工作環境
隔離環境（sandbox）
虛擬機（VM）/ 瀏覽器（browser）
受雲端授權與 approval 限制

能用工具 ≠ 有操作權限（Permission）。看得到工具，不代表這次就可以直接修改、發送或部署。

想 · 腦力激盪（Brainstorm）

先讓 AI 發散，
再由 Human 收斂

RUNNING EXAMPLE · LUT Gallery
1定義問題（Frame）「挑 LUT 太慢，我想降低比較成本。」
2發散（Diverge）
找相似自動分群並排比較搜尋改善
3挑戰 / 分群哪些解同一個問題？哪些成本太高？哪些需要更多資料？

AI 幫你擴大選項；不要在發散階段就急著選答案。

拆 · 工作層級

先分工作層級，
再談它現在做到哪

RUNNING EXAMPLE · LUT Gallery
Milestone｜里程碑 / 交付節點降低挑 LUT 的認知負荷
Epic｜主要能力 / 大主題改善 LUT 探索
Story｜使用者要得到的結果從喜歡的 LUT 找到相似候選
Task｜可以直接執行的工作加入「找相似」入口 + 候選結果列表

工作層級回答：「它屬於哪一層？」 下一頁的工作狀態板才回答：「它現在在哪？」

票 · 工作票（Ticket）+ 驗收條件（Acceptance Criteria）

工作票要讓別人不用猜；
AC 要能明確通過 / 不通過

#42從喜歡的 LUT 找到相似 LUT

範圍（Scope）

從既有 LUT 找相似候選。

不做 Auto-group；不做 LUT Editor。

Agent A · P1 · 改善 LUT 探索

驗收條件（AC）

① 點「找相似」後出現候選
② 資料不足時有空狀態
③ 390px 手機寬度沒有水平捲軸

驗收證據（Evidence）

可操作預覽 + 桌機 / 手機截圖 + 自動檢查

工作票 + AC→優先順序 / 相依性檢查→待辦（Backlog）

AC = 可觀察、可明確通過 / 不通過的完成條件。 Evidence = 審查時 reviewer 要實際檢查的證據。 工作票寫完整，不代表現在就應該做。

審 · 審查 / 驗收（Review / Acceptance）

Agent 說「完成」
只代表可以開始審查

RUNNING EXAMPLE · PR #71
PR #71 · 找相似 LUT
驗收證據可操作預覽 + 截圖 + 自動檢查 ✅
AC 1點「找相似」會出候選 ✅
AC 2資料不足有空狀態 ✅
AC 3390px 手機寬度沒有水平捲軸 ❌
已知限制尚未做自動分群；符合明確不做的範圍
你會通過（Approve）嗎？建置 / 測試都通過，但 AC 3 失敗。
通過（Approve）
退回修改（Request Changes） ✓一條已約定的 AC 失敗，就還不能過。

審查要看：驗收證據 + AC + 範圍 + 已知限制 + Human 決定。Agent 自己說完成、自動檢查通過，都不等於自動驗收。

選修 · Human 角色

先定 Human 的責任；
再談 Agent 可以扮演什麼角色

PM｜產品 / 專案負責人目標 · 優先順序 · 範圍 · AC · 驗收
UI/UX｜介面 / 體驗設計使用者流程 · 狀態 · 互動 · 視覺規格
FE｜前端介面 · 前端行為 · 串接
BE｜後端API · 資料 · 權限驗證 · 商業邏輯
Reviewer / QA審查 / 品質驗證 · 獨立驗證

Agent 可以做某個角色的工作；Human 的最終責任不會因為用了 Agent 就消失。

選修 · Agent 架構

後面的能力都只是插回五個位置；
Agent loop 沒有換一套

01指令（Instructions）專案規則 / Skills
例：AGENTS.md · CLAUDE.md
02工作脈絡（Context）目前工作 / 檔案 / 查回來的專案知識
例：可選的產品記憶（Memory）
03工具（Tools）可以呼叫的外部能力
例：內建工具 · Web Search · MCP · Connectors
04執行環境（Environment）動作在哪裡執行
例：本機 · 雲端隔離環境
05權限（Permissions）哪些讀取 / 修改 / 執行需要 Human 確認

回想 Slide 4：輸入 → LLM → 動作 → 觀察結果。產品記憶可以提供工作脈絡；它不是專案的正式依據。

選修 · 能力地圖

不要先把工具裝滿；
先問你缺什麼能力

每次都要照同一套方法？→ Skill｜可重用工作方法
要找公司 / 專案私有知識？→ RAG｜先檢索，再回答
要接外部工具 / 資料介面？→ MCP｜外部能力連接協定
要把 SaaS / 帳號能力接進產品？→ Connector / Plugin｜產品整合
要隔離專責工作者 / 工作脈絡？→ Subagent｜獨立工作者 / 工作脈絡
大型交付需要更完整的規格 / 規劃方法？→ SDD / BMAD｜大型交付方法

這不是名詞表。先遇到能力缺口，再加工具 / 方法。
